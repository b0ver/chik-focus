# Проверки, выпуск и восстановление

## Перед изменением

Выполнить `git status --short --branch`, работать в отдельной ветке. Проверить, что секреты исключены: `git check-ignore .env.local .local/backup.csv`. Не добавлять реальные данные участников в тесты и репозиторий.

## Проверки

Node.js 22. После изменения `dist/` выполнить:

```sh
node scripts/build.mjs
node scripts/check.mjs
node --test tests/*.test.mjs
```

Проверка проверяет синтаксис JS/Apps Script, JSON, локальные ссылки из HTML, характерный шаблон Telegram-токена и точное соответствие `docs/` свежей сборке. Это ограниченная проверка секретов, не полный аудит. Сборка проверяется во временной папке без перезаписи рабочих файлов. Для проверки интерфейса отдельно пройти изменённые сценарии в браузере и на телефоне.

## GitHub

Workflow `Quality and Pages`: PR → job `quality`; main → `quality` → публикация Pages. Workflow должен быть закоммичен и отправлен на GitHub. В Settings → Pages выбрать GitHub Actions; старый режим публикации branch/docs обходит этот workflow. Защита main должна требовать PR, успешную проверку `quality`, запрещать force push и удаление ветки, распространяться на администраторов. При единственном владельце обязательный чужой review не устанавливать.

Перед слиянием проверить изменения, зелёный CI и отсутствие секретов. После деплоя открыть публичную страницу, проверить основной сценарий, записать commit SHA и URL успешного запуска Actions в релизе. Успешный job не заменяет проверку интерфейса и внешних сервисов.

## Откат интерфейса

Найти SHA последнего рабочего релиза в успешном запуске Actions. Создать ветку из main, выполнить `git revert <SHA_плохого_коммита>` (для нескольких коммитов — от новых к старым), запустить проверки, открыть PR и слить после зелёного CI. Проверить успешную повторную публикацию и страницу без старого кеша. Не применять reset/force push. Если причина в самом workflow, исправление workflow тоже проходит PR.

## Сервер Apps Script и данные

GitHub Actions публикует только интерфейс. Apps Script обновляется отдельно. До изменения сохранить номер текущей версии и deployment ID приватно в `.local/`, отметить соответствующий Git SHA. Скопировать исходники текущей версии, если они отличаются от Git. До изменений структуры данных создать приватную копию таблицы средствами Google Sheets и проверить, что она открывается, содержит все листы, заголовки и ожидаемое число записей. Не менять публичный `/exec` URL при обновлении существующего deployment.

При сбое новых записей выполнить `closeBookings` в Apps Script. Для отката кода открыть Deploy → Manage deployments, изменить существующий deployment на сохранённую рабочую версию, сохранив URL. Проверить доступность API и отмену/восстановление тестовой записи. Проверить совместимость старого кода с текущими колонками и настройками. Откат кода не отменяет записанные данные и не возвращает удалённые строки.

Восстановление данных выполнять при закрытой записи: создать копию повреждённой таблицы, сверить резервную копию и изменения после неё, восстановить только необходимые строки/листы. Не затирать новые брони старым полным дампом. Сначала отрепетировать на отдельной приватной таблице и тестовом deployment; сравнить ID, статусы и число броней, проверить отсутствие дубликатов, восстановление по токену и отмену. Только затем открыть запись через `setup` и проверить состояние триггеров. Конфигурацию owner-бота сверять отдельно; повторная отправка уведомлений может дать дубликаты.

Автоматизированного резервного копирования, проверки восстановления и мониторинга сейчас нет. Целевые RPO/RTO пока не определены; инструкция выше не является свидетельством выполненного восстановления. До расширения реального использования нужно назначить ответственного, частоту приватных копий и провести восстановление на тестовой таблице. Script Properties и конфигурацию триггеров сохранять отдельно от копии Sheets в приватном хранилище.
